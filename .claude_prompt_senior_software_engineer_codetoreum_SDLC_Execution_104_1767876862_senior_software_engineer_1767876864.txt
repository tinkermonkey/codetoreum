**Base Event Protocol** (create in `src/codetoreum/ports/output/event_emitter.py`):
```python
from abc import ABC, abstractmethod
from typing import Callable, List
from codetoreum.domain.events import CodetoreumEvent

class IEventEmitter(ABC):
    """Event emission capability for adapters."""
    
    @abstractmethod
    def on(self, event_type: str, handler: Callable[[CodetoreumEvent], None]) -> None:
        """Subscribe to events of a specific type."""
        pass
    
    @abstractmethod
    def off(self, event_type: str, handler: Callable[[CodetoreumEvent], None]) -> None:
        """Unsubscribe from events."""
        pass
    
    @abstractmethod
    def emit(self, event: CodetoreumEvent) -> None:
        """Emit an event to all subscribers."""
        pass
```

## Executive Summary

This architectural analysis addresses the implementation of vendor-agnostic abstraction layers for Codetoreum, enabling the orchestrator to work seamlessly with multiple external systems (GitHub, JIRA, Trello, Azure DevOps, etc.) without coupling to vendor-specific implementations. The core design principle—event-based adapters where detection mechanisms are adapter-internal and the orchestrator receives standardized events—aligns well with the existing hexagonal architecture and complements the established port/adapter pattern already implemented in the codebase.

## System Architecture

- **Output Ports**: `ITicketSystem`, `ILLMProvider`, `IContainer`, `IRepository`, `IEventStore` (all in `src/codetoreum/ports/output/`)

## Scalability Design

### Event Distribution Architecture

The event system must support high-throughput event processing with multiple subscribers:

```python

│                                                             │

│                              │                              │

└────────────────────────────────────────────────────────────┘
```

**Throughput Considerations**:
- Board column changes: ~100-1000/day per project (bursty)
- Discussion comments: ~50-500/day per project
- Code review status changes: ~10-100/day per project
- Pipeline lock events: ~100-500/day per project

The existing Redis Streams + Elasticsearch infrastructure (documented in `03_implementation_plan.md`) can handle these volumes with margin.

### Detection Mechanism Scaling

Each adapter encapsulates its detection mechanism:

| Adapter | Mechanism | Scaling Characteristics |
|---------|-----------|------------------------|
| GitHub | Webhooks preferred, polling fallback | Webhook: no polling overhead; Polling: ~6000 req/hr limit |
| JIRA | Webhooks or JQL polling | Webhook preferred; Polling intervals configurable |
| Trello | Webhooks (required) | Rate limits: 300 req/10s, 100 req/10s per token |
| Azure DevOps | Service Hooks | Near real-time; queue-based delivery |

Adapters should implement **adaptive polling** when webhooks unavailable:
- Exponential backoff during low-activity periods
- Burst capacity during high-activity periods
- Respect per-vendor rate limits via existing `IRateLimiter`

### Horizontal Scaling Patterns

For multi-instance deployments:
1. **Event Deduplication**: Use `event_id` for idempotent processing
2. **Partition by Project**: Each instance handles subset of projects
3. **Leader Election**: For lock service coordination (Redis-based)

## ADR: Event-Based vs Polling-Based Orchestrator Integration

### Context

The orchestrator needs to react to external changes (work items moving between columns, new comments, PR approvals). Two approaches exist:
1. **Polling-based**: Orchestrator polls adapters periodically
2. **Event-based**: Adapters emit events, orchestrator subscribes

### Decision

**Adopt event-based adapters where detection mechanisms are adapter-internal.**

### Rationale

1. **Vendor Flexibility**: Each vendor has different optimal detection mechanisms (GitHub webhooks, JIRA JQL polling, Trello webhooks). Encapsulating detection inside adapters allows each to use its optimal approach.

2. **Clean Separation**: Orchestrator logic doesn't depend on detection method. A `workitem.column_changed` event is handled identically whether it came from a GitHub webhook or JIRA polling.

3. **Testability**: Mock adapters can emit events directly without simulating polling or webhook infrastructure. This enables deterministic, fast simulation tests.

4. **Consistency with Architecture**: The existing event-sourcing infrastructure (`IEventStore`, `EventBus`) already provides event distribution. Extending this to adapter events maintains architectural consistency.

### Consequences

- **Positive**: Cleaner orchestrator code, better testability, vendor flexibility
- **Negative**: Slightly more complex adapter implementations (must manage detection lifecycle)
- **Mitigation**: Provide base classes and mixins for common detection patterns

## ADR: Terminology Standardization

### Context

GitHub uses terms like "Issue", "Pull Request", "Projects v2 Status Field". JIRA uses "Issue", "Pull Request" (via Bitbucket), "Board". The codebase needs consistent terminology.

### Decision

**Adopt vendor-agnostic terminology as specified in the requirement:**

| Vendor Term | Standard Term |
|-------------|---------------|
| Issue (GitHub/JIRA) | Work Item |
| Issue Number | Work Item ID |
| Projects v2 | Project Board |
| Status Field | Column / Workflow State |
| Pull Request / Merge Request | Code Review |
| Issue Comment / PR Comment | Comment |

### Rationale

1. **Mental Model**: Developers working with Codetoreum shouldn't need to think in GitHub terms when the system supports multiple vendors.

2. **Interface Stability**: Using vendor-neutral terms in interfaces means interfaces don't change when adding vendors.

3. **Documentation Clarity**: Simulation scenarios and test cases use consistent terminology.

### Consequences

- **Positive**: Cleaner domain model, easier multi-vendor support
- **Negative**: Adapters must translate terminology at boundaries
- **Mitigation**: Use consistent mapping utilities; document term mappings per vendor

## Security Considerations

### Event Data Sensitivity

Events may contain sensitive information (work item titles, code review comments). Ensure:
1. Events in Redis Streams have appropriate TTL (2 hours per existing design)
2. Elasticsearch event indices follow retention policy (90 days)
3. Mock adapters don't log sensitive data in test output
4. Webhook endpoints validate signatures (GitHub: `X-Hub-Signature-256`)

### Identity Service Security

`IIdentityService` must not expose authentication tokens. It only answers:
- "Is this username a bot?"
- "What is the configured bot username?"
- "Filter human users from this list"

Configure via `BotIdentityConfig` without hardcoded values.
