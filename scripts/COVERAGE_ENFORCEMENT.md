# Coverage Enforcement Infrastructure

This document describes the per-layer coverage enforcement infrastructure for the Codetoreum project.

## Overview

The coverage enforcement infrastructure ensures that code quality meets architectural standards by enforcing coverage thresholds at different layers of the hexagonal architecture:

- **Domain Layer** (`src/codetoreum/domain/`): 100% coverage required
- **Application Layer** (`src/codetoreum/application/`): 90% coverage required
- **Overall**: 80% coverage required

## Architecture

### Components

1. **enforce_coverage.py** - Main enforcement script that:
   - Runs pytest with coverage collection
   - Parses coverage.json to extract per-layer metrics
   - Compares metrics against thresholds
   - Reports clear pass/fail status for each layer
   - Exits with code 1 if any threshold is violated

2. **pyproject.toml** - Coverage configuration:
   - Specifies coverage source and omit patterns
   - Configures coverage report options
   - Documents per-layer enforcement requirements

3. **Makefile** - Build automation:
   - `test-cov` target: Generates HTML and JSON coverage reports
   - `test-cov-enforce` target: Runs tests and enforces per-layer thresholds

4. **CI Workflow** (.github/workflows/ci.yml):
   - Runs per-layer coverage enforcement as part of CI pipeline
   - Fails build if any threshold is violated

## Usage

### Local Development

Run tests with per-layer coverage enforcement:

```bash
make test-cov-enforce
```

Generate coverage reports (HTML, XML, and JSON):

```bash
make test-cov
```

View HTML coverage report:

```bash
open htmlcov/index.html
```

### CI Pipeline

Coverage enforcement runs automatically as part of the CI workflow when enabled:

```yaml
- name: Run tests with per-layer coverage enforcement
  run: python3 scripts/enforce_coverage.py
```

## Implementation Details

### Coverage Metrics Extraction

The script parses `coverage.json` generated by pytest-cov and extracts metrics by analyzing file paths:

1. **Layer Identification**: Files are matched to layers based on path patterns:
   - Domain: `src/codetoreum/domain`
   - Application: `src/codetoreum/application`

2. **Line Counting**: For each matched file, the script counts:
   - Total lines of code (statements)
   - Covered lines
   - Percentage coverage = (covered_lines / total_lines) × 100

3. **Threshold Comparison**: Per-layer and overall percentages are compared against minimum thresholds

### Exit Codes

- **0**: All coverage thresholds met
- **1**: One or more thresholds violated

### Output Format

The script produces clear, structured output:

```
================================================================================
Coverage Enforcement Results
================================================================================
✓ PASS Domain        100.00% (500/500 lines) [required: 100.00%]
✓ PASS Application    92.50% (740/800 lines) [required: 90.00%]
✓ PASS Overall        85.30% (3200/3750 lines) [required: 80.00%]
================================================================================
```

## Rationale for Thresholds

### Domain Layer (100%)

The domain layer contains pure business logic with no external dependencies. Due to its criticality:
- Pure functions are highly testable
- 100% coverage is achievable and recommended
- Business logic must be thoroughly validated

### Application Layer (90%)

Application services orchestrate domain logic and coordinate with external systems. 90% is chosen because:
- Some error paths involving external failures are difficult to test deterministically
- Infrastructure concerns (timeouts, retries) may have hard-to-test paths
- Core orchestration logic should be thoroughly covered

### Overall (80%)

The overall threshold accounts for infrastructure and adapters:
- **80%** provides a healthy safety net across the entire codebase
- Adapters to external systems may have platform-specific code that's harder to test
- Configuration and utility code may not always require full coverage

## Enforcement Strategy

### Multi-Layer Approach

The enforcement uses a belt-and-suspenders approach:

1. **Primary**: `enforce_coverage.py` script with per-layer thresholds
   - Provides clear per-layer reporting
   - Enables architectural layer protection
   - More maintainable than configuration-based enforcement

2. **Secondary**: `pyproject.toml` fail_under setting (80%)
   - Safety net if script fails
   - Standard pytest-cov configuration
   - Fallback for local development

### When Thresholds Fail

If coverage enforcement fails:

1. **Identify**: Which layer(s) or overall coverage is below threshold
2. **Analyze**: Which files or functions lack coverage
3. **Add Tests**: Write tests to cover missing paths
4. **Verify**: Re-run `make test-cov-enforce` to verify passing

Use HTML coverage reports to identify uncovered lines:

```bash
make test-cov
open htmlcov/index.html
```

## Troubleshooting

### Script Fails to Find pytest

**Issue**: `Error: [Errno 13] Permission denied: 'pytest'`

**Solution**: Ensure the virtual environment is set up:
```bash
poetry install
# or
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
```

### coverage.json Not Found

**Issue**: `Error: coverage.json not found`

**Solution**: This usually means tests failed to run. Check:
1. All dependencies are installed
2. Tests directory structure is correct
3. pytest-cov is installed in the virtual environment

### Thresholds Too Strict

If you need to adjust thresholds, modify `COVERAGE_THRESHOLDS` in `enforce_coverage.py`:

```python
COVERAGE_THRESHOLDS = [
    CoverageThreshold(name="Domain", path_pattern="src/codetoreum/domain", minimum_percent=95.0),
    CoverageThreshold(name="Application", path_pattern="src/codetoreum/application", minimum_percent=85.0),
]
OVERALL_MINIMUM_PERCENT = 75.0
```

## Best Practices

1. **Run Locally First**: Always run `make test-cov-enforce` locally before pushing
2. **Review Coverage Reports**: Use HTML reports to understand what's not covered
3. **Domain-First Testing**: Prioritize domain layer test coverage (100% requirement)
4. **Integration Tests**: Application layer tests should focus on integration scenarios
5. **Regular Monitoring**: Track coverage trends over time
